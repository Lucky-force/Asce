# 单位模块化 / 单位编辑器（需求与方向）

> 状态：**验证结论 + 方向**，未实现。
> 目标：把"结构靠 trait（模板资产）、数值靠 def 表"的两处配置，收敛成**一个单位 = 一行数据 = 一组功能模块**；
> 结构由模块组合决定（背后仍是 fragment），数值在模块里填；配一个可视化编辑器做增删 + 预览。
>
> 相关：`Data/AsceEntityDefTypes.h`、`Data/AsceUnitDef.h`、`Traits/*`、`Combat/技能编辑器设计.md`、`Building/建筑系统设计.md`、`Ether/Ether系统设计.md`。

---

## 0. 问题陈述

| 现状 | 问题 |
|---|---|
| 结构写在 trait（`UMassEntityConfigAsset` 里），一个类型一个模板资产 | 抽象极高，配置者要懂 fragment；N 个类型 = N 个模板，且无法 diff |
| 数值写在实体定义表 `FAsceEntityDefRow.Def` | 数值和结构分两处，容易配错（比如配了攻击行但没挂战斗模块） |
| 错配无校验 | 全靠运行时 `ensure` / 日志发现 |
| archetype 成本不可见 | 不知道"再加一个能力"要多花多少内存/多出几种 archetype |

**目标**：模块 = 面向策划的抽象，内部映射到 fragment/tag；编辑器负责"加模块 + 填数值 + 预览 + 校验 + 生成模板"。

## 2. 模块划分（结论）

### 2.1 基础层（**不做模块**，所有实体都有）
Transform / Identity(`UnitDef`) / Team / Lifecycle / AliveTag / 复制 / 行为树（def 可选覆盖，空 = 通用树）

> 理由：人人都有 + 组成 archetype 的共同部分；做成模块只会让每行都勾一遍。

### 2.2 功能模块

| 模块 | 含 fragment / tag | 依赖 | 对应表字段 |
|---|---|---|---|
| **Health** | `FAsceHealthFragment` | — | `MaxHealth` |
| **Volume** | `FAgentRadiusFragment` + `FAsceHeightFragment` | — | `Radius` / `Height` |
| **Movement** | Velocity / Force / DesiredMovement / CodeDrivenTag / MovementTuning / MoveOrder / SimState / PositionCorrection / MovableUnitTag | **Volume** | `MaxSpeed` / `MaxAcceleration` / `DefaultDesiredSpeed` |
| **Vision** | `FAsceVisionViewFragment` + `FAsceVisionFogStateFragment` | **Volume**（眼高取 `Height`） | `SightRadius` |
| **Combat** | `FAsceCombatFragment` | **ActionState** | `AttackRange` / `AttackDamage` / `AttackSpeed` / `bAutoAttackDefault` / `AttackAction`（+ 旧 `AttackCastConfig` 迁移兜底） |
| **Skills** | `FAsceSkillSlotsFragment` + `FAsceManaFragment` | **ActionState** | `MaxMana` / `SkillSlots[3]` |
| **ActionState** | `FAsceActionFragment` + `FAsceCombatVisualFragment` | — | （无，纯逻辑+下发） |
| **Animation** | `FAsceAnimPlaybackFragment` | ActionState（语义上） | `AnimSet` / `IdleAnim` / `MoveAnim` / `DyingAnim` / `IdleAnimVariants` / `MoveAnimVariants` / `MoveAnimRunSpeedCm` |
| **Interaction** | `FAsceInteractableFragment` + `PlayerOnly`/`Generic` tag | **Volume** | `InteractionRange` / `bPlayerOnlyInteraction` |
| **Building** | `FAsceBuildingTag`（+ 建造两段由建筑系统负责） | — | `SizeX/SizeY` / `OcclusionHeightCm` / `BuildTimeSeconds` / `CoreClass` |
| **Ether** | `FEtherBuildingFragment`（+ 端口/核心在子系统） | **Building** | `FAsceEtherBuildingDef` 的全部字段 |

### 2.3 图的依赖（模块勾选时的强制/提示）
```
Volume ──> Movement
   └────> Vision
   └────> Interaction
ActionState ──> Combat
            └─> Skills
Animation  （独立，建议与 ActionState 一起勾）
Building ──> Ether
```

## 3. 合并 / 拆分决策（含被否方案）

| 决策 | 理由 |
|---|---|
| **Volume 从 Movement 拆出** | 现状 `Radius/Height` 无条件挂，但 `Movement` 由 `bCanMove` 控制。炮塔/固定炮台/建筑需要体积（选择、命中、视野眼高）但不动；建筑进建筑层不需要 Volume，而"固定单位"需要。拆开才能表达"有体积、不能动" |
| **Mana 不并进 Health，并进 Skills** | 只有技能消耗蓝；纯血牛单位带 8B 蓝没意义。放进 Skills 后"没蓝量字段"天然等于"不能放技能" |
| **ActionState 与 Animation 拆开** | `FAsceActionFragment` 是**逻辑**（战斗/技能/移动表现都依赖它），`AnimPlayback` 是**表现**。无头/纯逻辑单位（投射物、纯服务端代理）可只挂 ActionState |
| **Combat 不并进 ActionState** | "能被打"靠 Health（所有单位都有），"能打"才是 Combat。合并会让所有单位多背 48B + 一堆攻击数值 |
| **Skills 不并进 Combat** | 纯施法单位（`bCanAttack=false`）是合法存在（见风险 §6.2）；且技能槽/CD 与普攻完全无关 |
| **不做 Render 模块** | 现在渲染没有自己的 fragment（用 `AnimPlayback` + 表里的动画/模型引用）。将来真加表现 fragment（模型索引/材质参数）再拆一个 |
| **Replication 不做模块** | 所有要同步的实体都要；差异只在 `ReplicationTuning` 数值（放模块外部，或建成基础层的"同步配置"） |
| **行为树不做模块** | 它是 const shared fragment（per archetype），且计划是"一棵通用树 + capability tag"；做成模块会把 archetype 数量再乘一遍 |
| **"寻路"不单独成模块** | 现在没有独立 fragment，寻路是移动的隐含能力（costfield 查询）。以后加飞行/穿墙再拆 `Navigation` 模块 |
| **Interaction 独立** | 与移动/战斗无关（建筑也能可交互）；依赖 Volume 是因为交互距离/体积判定 |

结论：
1. **6 个典型单位全部可表达**，且"固定炮塔"正好验证了 Volume/Movement 拆分的必要性（有体积、不能动、能攻击）。

## 5. 落地方向

### 5.1 模块数据结构
```cpp
USTRUCT()
struct FAsceUnitFeatureModule   // 作为 FInstancedStruct 存在列表里
{
    virtual FName GetModuleId() const;                                     // "Movement"
    virtual FText GetDisplayName() const;
    virtual void BuildFragments(FMassEntityTemplateBuildContext&) const;   // 模板期：加 fragment/tag
    virtual void ApplyNumbers(FMassEntityManager&, FMassEntityHandle, const FAsceEntityDefRow&) const; // spawn 期：写值
    virtual void Validate(const FAsceEntityDefRow&, TArray<FText>& OutErrors) const;  // 依赖/冲突
    virtual void DrawPreview(const FAsceUnitPreviewContext&) const;        // 编辑器预览
};
```
模块自己就是数值容器（`MaxSpeed`、`SightRadius`…），迁移时把 `FAsceRTSUnitDef` 的顶层字段按功能搬进对应模块。

### 5.2 单一数据入口
```cpp
// def 表行里
TArray<FInstancedStruct> Modules;   // 结构与数值的唯一定义

// 模板侧
UAsceModularUnitTrait { FAsceRowNameWrapper UniqueType; }  // BuildTemplate 时读该行的 Modules，逐个 BuildFragments
```
- **为什么结构也要进 def 行**：`BuildTemplate` 本来就要 load def 行（现在为读 `StateTree` 已在做），顺手读模块列表零成本；反过来把模块放 trait 里会让"N 个模板资产"变成真相来源，diff 不可读。
- 结构必须在**模板期**决定（fragment 集合 = archetype 身份），所以模块列表必须能被 `BuildTemplate` 看到。

### 5.3 模板落地的两条路
| 路线 | 做法 | 何时用 |
|---|---|---|
| **A. 生成模板资产** | 编辑器按"模块组合"去重，生成/更新 `UMassEntityConfigAsset`，自动填 `Row.EntityTemplate` | 先做，零运行时风险 |
| **B. 运行时组合** | 直接 `GetOrCreateArchetype(Composition, SharedFragmentValues)` 按 def 行缓存 | 后做，可支持热改；需处理 const shared（树/复制参数） |

### 5.4 编辑器预览分级
| 级别 | 内容 | 备注 |
|---|---|---|
| L1 | 占格框 / 视野圈 / 攻击圈 / 数值标注 / **fragment 清单 + 每实体字节 + archetype 组合统计** | 必做，性价比最高 |
| L2 | 直接播动画资产（Idle/Move 变体、Attack 片段），不走 Mass，不需要 PIE | 强烈建议 |
| L3 | 隔离 preview world 里真跑 Mass + StateTree + VAT，输入切状态 | 单独立项 |

### 5.5 动画数据归属（**不要** archetype shared data）

| 动画 | 归属 | 理由 |
|---|---|---|
| Idle / Move（含 Run 变体、变体数组） | 单位表 → Movement / Animation 模块 | 连续状态，与动作无关 |
| Dying | 单位表 → Animation 模块 | 同上 |
| **Attack** | 单位表 → Combat 模块（`AttackAnimVariants[]`） | CastConfig 退役后，攻击动画跟单位走（见 §5.6） |
| 技能 / 其它"动作" | **技能子树资产**（按 `ActionId` 查表） | 时长/动画是技能本身的属性，跨单位共享 |

**为什么不用 const shared fragment / per-entity fragment：**
- 现状已经是"**表 + 类型级缓存**"：`UAsceCombatVisualProcessor` 里 `AnimSetCache` / `AnimRefCache` 都是 `TMap<UnitTypeId, …>`，
  只在**状态边沿**（`Counter` / `ActionState` / `bValid` / `MoveBucket` 变化）做一次 `FindOrLoadAnimSet` + `ResolveClipRef`，
  之后每帧只推进帧号（纯算术）。
- 放 const shared：省掉"边沿时的一次 TMap find"，但**archetype 会按动画集分叉**（同结构不同动画 = 不同 archetype），
  与"合并 archetype"目标相反；且 `FAsceUnitAnimRefs` ≈ 300~500B，shared 也是每 archetype 一份，和现在"每类型一份"等价。
- 放 per-entity：N × 300~500B，直接灾难。
- 唯一值得优化的是首帧 `LoadSynchronous` 的卡顿（改异步预热/AssetBundle），与 shared data 无关。

### 5.6 攻击：**通用子树 + 数据驱动的时间轴/动画**（CastConfig 退役）

目标：所有单位共用一棵"攻击子树"；前摇/后摇/动画都在**单位配置**里配（可视化面板），不再为改动画复制子树。

**硬约束**：StateTree 的节点时间是**静态常量**（`FAsceWaitTimelineTask` 的 `Time` 是实例数据里的 EditAnywhere 常量）
⇒ 必须有一个"**数据驱动的等待 task**"。

```cpp
// 新增（~70 行），替代攻击流程里写死时间的 wait
UENUM() enum class EAsceActionPhase : uint8 { Windup, Recovery };

USTRUCT(meta=(DisplayName="Asce Wait Action Phase"))
struct FAsceWaitActionPhaseTask : public FMassStateTreeTaskBase
{
    UPROPERTY(EditAnywhere) EAsceActionPhase Phase = EAsceActionPhase::Windup;
    // EnterState: 读 FAsceUnitDefFragment.UniqueTypeId → 实体定义行（有缓存）→ 前摇/后摇时长
    //             → 存"相对动作起点的门槛"到实例数据 → AsceTimeline::HasReached(...)（与现有 wait 语义一致）
    // Tick:       同现有 wait（时间轴绝对服务器时间，不累加 delta）
    // 依赖：FAsceUnitDefFragment(ReadOnly) + FAsceBehaviorFragment
};
```

> **从哪里读时长**：读**复制的属性 fragment**（§5.7 的 `FAsceCombatAttributesFragment`，树两端都能拿到），
> 而不是服务器专有的 `FAsceCombatFragment`、也不是查定义行 —— 两端读同一份复制值 + `FAsceBehaviorFragment`
> 锚定服务器起点 ⇒ 前摇/后摇天然一致。

**单位侧新增数据（Combat 模块）**
| 字段 | 用途 |
|---|---|
| `AttackWindupSeconds` | 前摇（动作开始 → 结算） |
| `AttackRecoverySeconds` | 后摇（结算 → 动作结束） |
| `AttackAnimVariants[]` | 攻击动画随机数组（按 `VariantSeed`/`Counter` 取一个） |

spawn 时同时写进 `FAsceCombatFragment`（`AttackTriggerTime = Windup`、`AttackTotalTime = Windup + Recovery`）供服务器结算用；
`AttackSpeed` 继续决定 `PlayRate`。

**通用攻击子树形状**
```
Idle --[事件 Asce.Action.Attack]--> Attack
  ├ Asce Set Action State(Attack)      // 写动作态（两端）
  ├ Asce Wait Action Phase(Windup)
  ├ Asce Settle Skill(bPayCost=false)  // 结算（内部带 bTriggered 防重复）
  ├ Asce Wait Action Phase(Recovery)
  └ 完成 → Idle
```

**动画解析**：`FAsceUnitAnimRefs` 增加 `AttackVariants`（由 def 的 `AttackAnimVariants` 构建），视觉处理器在
`ActionState==Attack` 时按 `VariantSeed`/`Counter` 选一个（`FAsceUnitAnimRefs` 的缓存机制不变，仍是每类型一份）。

**技能不同**：技能的时间轴/动画属于**技能子树资产**（按 `ActionId` 查表），跨单位共享；攻击是"每单位数据 + 共享子树"。
两者不冲突。

**迁移**：`FAsceActionDef::CastConfig` / `FAsceRTSUnitDef::AttackCastConfig` / 攻击动作行的 `CastAnim` 逐步退役；
先保留 `AttackAction`（只作为"用哪个动作/是否 Auto"的兼容标记），后续评估是否连它也去掉。

### 5.7 模块内的 fragment 两分法：**属性（复制）** + **运行态（权威/本地）**

> 原则：一个功能模块 = **属性 fragment**（纯数据，客户端要读的就开复制）+ **运行态 fragment**（服务器专有或本地）。
> 先例：Health/Mana 已经就是这个形态（`FAsceHealthFragment` / `FAsceManaFragment` 走"值通道"复制）。

| 模块 | 属性 fragment（复制条件） | 运行态 fragment（服务器/本地） |
|---|---|---|
| Health | `FAsceHealthFragment`（**已复制**：Max/Current） | — |
| Mana | `FAsceManaFragment`（**已复制**：Max/Current） | — |
| Movement | `FAsceMovementTuningFragment`（MaxSpeed/MaxAccel/DesiredSpeed；**当前不复制**，客户端动画用实际速度） | Velocity / Force / DesiredMovement / MoveOrder / SimState / PositionCorrection |
| Combat | **新增** `FAsceCombatAttributesFragment`（**复制**：Damage/Speed/BaseWindup/BaseRecovery/Range/bAutoAttack） | `FAsceCombatFragment`（瘦身：DesignatedTarget / NextScanTime） |
| Vision | `FAsceVisionViewFragment`（SightRadius/EyeHeight；**不复制**，雾在服务端算） | `FAsceVisionFogStateFragment`（本地） |
| Skills | `FAsceSkillSlotsFragment`（**已复制**：槽位 + CD） | — |
| Interaction | `FAsceInteractableFragment`（Range；**不复制**，判定在服务端） | — |

**只复制"客户端真的会读"的**：Combat 属性必须复制（客户端也要跑攻击子树、要算 PlayRate/动画、要显示攻击范围）；
Movement 的 MaxSpeed 客户端用不到（动画按实际速度选 Run 桶），先不加通道，避免白花带宽。

**`FAsceCombatAttributesFragment` 字段（20~21B）**
```cpp
float AttackDamage;        // 显示/结算
float AttackSpeed;         // 180 = 1.0x；决定 PlayRate 与前后摇
float BaseWindupSeconds;   // 基础前摇
float BaseRecoverySeconds; // 基础后摇
float AttackRange;         // 攻击距离（UI 指示器 + 服务端判定）
bool  bAutoAttack;         // 玩家可切（UI 也要读）
```

**攻速 → 动画/时长统一换算（关键：必须用同一个 PlayRate，否则命中帧和结算错位）**
```cpp
PlayRate       = clamp(AttackSpeed / 200 + 0.1, 0.1, 4.0)   // 180 → 1.0
ActualWindup   = BaseWindupSeconds   / PlayRate
ActualRecovery = BaseRecoverySeconds / PlayRate
TriggerTime    = 动作起点 + ActualWindup
ActionEndTime  = 动作起点 + ActualWindup + ActualRecovery
```
- 动画也按同一个 `PlayRate` 播 ⇒ "动画播到命中帧" 与 "逻辑结算时刻" 一致；
- clamp 上下限防止攻速极高时前摇不足 1 帧、极低时动画拖太久；
- 绝对时刻只写在服务器侧 `FAsceActionFragment`（`TriggerTime/ActionEndTime`），客户端用自己锚定的时间轴推（`ActionStartTimeQ`）。

**新增一个复制通道的成本**（照 `AsceReplicationValueHandlers.h` 头注释的 5 步）
1. 选/加值容器 USTRUCT（已有 `FReplicatedValueFloat`，直接用）；
2. 写 `FAsceCombatAttributesPolicy`（FragmentType / NumFields / Get(Mutable)Data / ExtractFromFragment / ApplyToFragment / ValuesDiffer）；
3. `using FAsceCombatAttributesClientBubbleHandler = TAsceValueClientBubbleHandler<...>;`
4. `using FAsceCombatAttributesReplicationCapability = TAsceValueReplicationCapability<...>;`
5. `AsceReplicationBootstrapSubsystem.cpp` 里 `RegisterCapability(MakeUnique<...>())` 一行。

> 净字节：`FAsceCombatFragment` 48B 里的 5 个静态 float 搬走后变成 ~28B，新增属性 20B ⇒ 总量基本不变，
> 但客户端能拿到攻速/前后摇/射程，且语义清晰（"属性" vs "运行态"）。


## 6. 风险 / 未决

### 6.1 archetype 组合爆炸
模块组合 = archetype。编辑器必须显示"当前全项目共有 N 种组合、各自多少单位"，并提示 chunk 浪费（128KB chunk 对几十个实体的 archetype 是浪费）。合并策略：能共用就共用（例如所有地面战斗单位统一勾 Health+Volume+Movement+Vision+ActionState+Animation+Combat）。

### 6.2 `bCanAttack=false` 目前会连技能一起废掉（**必须先修**）
`UAsceCombatProcessor` 的 query 把 `FAsceCombatFragment` 设为**必需**，而它是动作状态机（Move/Casting/Channel 推进）的唯一驱动者 ⇒ 没有战斗模块的单位：
- 技能 `Casting` 卡死、`ActionState=Move` 永远不写（走路不播动画）。
- 修法：把该 fragment 改成 `Optional`，攻击相关代码进 `if (bHasCombat)`；状态机无条件跑。或更彻底：拆出 `UAsceActionProcessor`（只要 `FAsceActionFragment`）。

### 6.3 通用树前提（否则"一棵树"不成立）
- `AsceSelectAnimVariantTask`（唯一和动画相关的 task，只写 `VariantSeed`）挪进 `UAsceStateTreeNotifyProcessor`
- 能力 tag（`Asce.Capability.Move/Attack/Cast`）+ `FAsceStateTreeTagCondition`（约 40 行）
- 之后 `FAsceEntityDefBase::StateTree` 留空 = 用通用树

### 6.4 编辑器成本主要在预览
L1 便宜；L2 要处理"编辑器里没有 Mass 世界"的资产加载；L3 是独立小项目（preview world 隔离、输入、状态驱动）。

### 6.5 迁移
现有 3 个 trait 的字段搬进模块；现有 def 行 + 模板资产一次性重生成；`UniqueTypeId` 改为 spawn 时写（`ApplyUnitDef`），trait 里 `UniqueType` 变可选覆盖。
