# 单位模块化 / 单位编辑器（需求与方向）

> 状态：**基础版已实现**（模块编辑器 / 生成器 / 新动画任务）；配置、数据迁移与验收进行中。
> 目标：把"结构靠 trait（模板资产）、数值靠 def 表"的两处配置，收敛成**一个单位 = 一行数据 = 一组功能模块**；
> 结构由模块组合决定（背后仍是 fragment），数值在模块里填；配一个可视化编辑器做增删 + 预览。
>
> 相关：`Data/AsceEntityDefTypes.h`、`Data/AsceUnitDef.h`、`Traits/*`、`Combat/技能编辑器设计.md`、`Building/建筑系统设计.md`、`Ether/Ether系统设计.md`。

---

## 0. 问题陈述

| 现状 | 问题 |
|---|---|
| 结构写在 trait（`UMassEntityConfigAsset` 里），一个类型一个模板资产 | 抽象极高，配置者要懂 fragment；N 个类型 = N 个模板，且无法 diff |
| 数值写在实体定义表 `FAsceEntityDefRow.Def` | 数值和结构分两处，容易配错（比如配了攻击行但没挂战斗模块） |
| 错配无校验 | 全靠运行时 `ensure` / 日志发现 |
| archetype 成本不可见 | 不知道"再加一个能力"要多花多少内存/多出几种 archetype |

**目标**：模块 = 面向策划的抽象，内部映射到 fragment/tag；编辑器负责"加模块 + 填数值 + 预览 + 校验 + 生成模板"。

## 2. 模块划分（结论）

### 2.1 基础层（**不做模块**，所有实体都有）
Transform / Identity(`UnitDef`) / Team / Lifecycle / AliveTag / 复制 / 行为树（def 可选覆盖，空 = 通用树）

> 理由：人人都有 + 组成 archetype 的共同部分；做成模块只会让每行都勾一遍。

### 2.2 功能模块

> **模块之间没有"依赖"关系**：每个模块自带自己的 fragment 闭包；多个模块撞上同一个 fragment 是合法的，
> 合成时按**并集**去重（谁"拥有参数"谁提供值，其余模块只是"需要它存在"，见 §2.3）。

| 模块 | 拥有（带参数的）fragment / tag | 需要存在（不提供参数） | 对应表字段 |
|---|---|---|---|
| **Health** | `FAsceHealthFragment` | — | `MaxHealth` |
| **Volume** | `FAgentRadiusFragment` + `FAsceHeightFragment` | — | `Radius` / `Height` |
| **Movement** | Velocity / Force / DesiredMovement / CodeDrivenTag / MovementShared(const) / MoveOrder / SimState / PositionCorrection / MovableUnitTag | Radius / Height | `BaseMoveSpeed`（奔跑/受伤阈值都由它推） |
| **Vision** | `FAsceVisionViewFragment` + `FAsceVisionFogStateFragment` | Height（眼高） | `SightRadius` |
| **Combat** | `FAsceCombatAttributesFragment`（属性，复制）+ `FAsceCombatFragment`（运行时） | Action / CombatVisual | `AttackRange` / `AttackDamage` / `AttackSpeed` / `RangeKind` / `AttackAction`（**前摇/后摇目前在攻击动作行的 SkillTree 节点里**，不在单位数据） |
| **Skills** | `FAsceSkillSlotsFragment` + `FAsceManaFragment` | Action / CombatVisual | `MaxMana` / `SkillSlots[3]` |
| **ActionState** | `FAsceActionFragment` + `FAsceCombatVisualFragment` | — | （无，纯逻辑+下发） |
| **Animation** | `FAsceAnimPlaybackFragment`（cue，客户端本地） | — | `AnimSet`（clip 目录）；**动画片段本身由树的 cue 节点 `Variants` 配**（见 §5.5） |
| **Interaction** | `FAsceInteractableFragment` + `PlayerOnly`/`Generic` tag | Radius | `InteractionRange` / `bPlayerOnlyInteraction` |
| **Visualization** | —（写 **EntityTemplate** 上的 `UMassMovableVisualizationTrait`：StaticMesh + TransformOffset） | — | `StaticMesh` / `LocalTransform` |
| **Building** | `FAsceBuildingTag`（+ 建造两段由建筑系统负责） | — | `SizeX/SizeY` / `OcclusionHeightCm` / `BuildTimeSeconds` / `CoreClass` |
| **Ether** | —（完工时由建筑子系统加 `FEtherBuildingFragment`） | BuildingTag | `FAsceEtherBuildingDef` 的全部字段 |

### 2.3 fragment 闭包重叠（**没有模块依赖**）
```
Radius/Height  ← 拥有者: Volume   ／ 需要它存在: Movement（避让）、Vision（眼高）、Interaction
Action/Visual  ← 拥有者: ActionState ／ 需要它存在: Combat、Skills
BuildingTag    ← 拥有者: Building ／ 需要它存在: Ether
```
- 合成 = **所有模块的 fragment 并集**（同类型只保留一份）；
- 值由**拥有者模块**提供（按注册表顺序先落地）；没有拥有者时用 fragment 默认值；
- 所以"Vision 没勾 Volume"也是合法的：它会自带一个默认的 `FAsceHeightFragment`（眼高 = 0/默认），不会报错；
- 编辑可以给**提示**（"这个组合会让半径走默认值 75"），但**不做强制依赖**。

## 3. 合并 / 拆分决策（含被否方案）

| 决策 | 理由 |
|---|---|
| **Volume 从 Movement 拆出** | 现状 `Radius/Height` 无条件挂，但 `Movement` 由 `bCanMove` 控制。炮塔/固定炮台/建筑需要体积（选择、命中、视野眼高）但不动；建筑进建筑层不需要 Volume，而"固定单位"需要。拆开才能表达"有体积、不能动" |
| **Mana 不并进 Health，并进 Skills** | 只有技能消耗蓝；纯血牛单位带 8B 蓝没意义。放进 Skills 后"没蓝量字段"天然等于"不能放技能" |
| **ActionState 与 Animation 拆开** | `FAsceActionFragment` 是**逻辑**（战斗/技能/移动表现都依赖它），`AnimPlayback` 是**表现**。无头/纯逻辑单位（投射物、纯服务端代理）可只挂 ActionState |
| **Combat 不并进 ActionState** | "能被打"靠 Health（所有单位都有），"能打"才是 Combat。合并会让所有单位多背 48B + 一堆攻击数值 |
| **Skills 不并进 Combat** | 纯施法单位（`bCanAttack=false`）是合法存在（见风险 §6.2）；且技能槽/CD 与普攻完全无关 |
| **不做 Render 模块** | 现在渲染没有自己的 fragment（用 `AnimPlayback` + 表里的动画/模型引用）。将来真加表现 fragment（模型索引/材质参数）再拆一个 |
| **Replication 不做模块** | 所有要同步的实体都要；差异只在 `ReplicationTuning` 数值（放模块外部，或建成基础层的"同步配置"） |
| **行为树不做模块** | 它是 const shared fragment（per archetype），且计划是"一棵通用树 + capability tag"；做成模块会把 archetype 数量再乘一遍 |
| **"寻路"不单独成模块** | 现在没有独立 fragment，寻路是移动的隐含能力（costfield 查询）。以后加飞行/穿墙再拆 `Navigation` 模块 |
| **Interaction 独立** | 与移动/战斗无关（建筑也能可交互）；它需要 Radius 存在（交互距离/体积判定），但**不是依赖 Volume 模块**——闭包里带上即可 |
| **攻击的时长/动画放"动作行"先于放"单位"** | `3c0db39` 后攻击 = 动作行 + `SkillTree`：同类武器（步枪/狙击)共用一行，时长与动画天然一致；按单位区分节奏是少数需求（见 §5.6） |
| **动画片段配置在树的 cue 节点** | 技能链/动作行仍如此（`FAscePlayAnimCueTask.Variants`）；单位 `Idle/Move/Attack` 已改由 `AscePlay*AnimTask` 读 def 的 `*Anims`（§5.5） |

## 5. 落地方向

### 5.1 分层：模块"数据"在运行时，模块"行为"在编辑器

| 位置 | 内容 |
|---|---|
| **`AsceEditor`** | 模块的**纯数据 USTRUCT**（`FAsceUnitModuleHealth{MaxHealth}`、`FAsceUnitModuleMovement{MaxSpeed…}`…）—— 只活在编辑器侧资产里，运行时不需要（运行时只有 fragment + def 引用）。 |
| **`AsceEditor`** | 每个模块**一个 .h/.cpp**（`Modules/AsceUnitModule<Name>.*`），行为用虚函数写在模块自己身上：`Contribute`（加哪些 fragment/tag + 数值）、`WriteDefRow`（非 fragment 字段）、`Validate`、`Preview`（后续 L1/L2 预览）；注册表只负责"列出类型 + 按顺序合成并集 + 校验"。 |
| **`AsceEditor`** | 每个"单位类型"的模块配置资产 `UAsceUnitModuleConfig`（模块列表 + 参数 + `Hash`）。 |
| **`AsceGame`** | `def 行`：只保留"引用 + 非 fragment 数据"（见 §5.8）+ `#if WITH_EDITORONLY_DATA` 的 `FSoftObjectPath ModuleConfig`。 |

关键：**运行时只看到"fragment（含初值）+ def 引用"**，不认识模块；模块的全部知识（哪个模块加什么、依赖谁、预览什么）都在编辑器。

### 5.1b DA 是标准资产，用引擎自带 trait

**不需要自己写 trait**：引擎已有 `UMassAssortedFragmentsTrait`（显示名 "Assorted Fragments"），
它的 `TArray<FInstancedStruct> Fragments` / `Tags` 就是"要加哪些 fragment/tag"，而且**带初值**：
```cpp
// MassSpawner/Private/MassAssortedFragmentsTrait.cpp
for (const FInstancedStruct& Fragment : Fragments)
    if (UE::Mass::IsA<FMassFragment>(Type)) BuildContext.AddFragment(Fragment);   // 带值
for (const FInstancedStruct& Tag : Tags) BuildContext.AddTag(*Type);
```
- DA 形状：`UAsceRTSEntityTrait`（基础：Transform/Identity/Team/Lifecycle/AliveTag/StateTree/复制委托）
  + **`UMassAssortedFragmentsTrait`（模块并集 + 数值）** + `UMassReplicationTrait`（tuning）；
- 它的 `Fragments/Tags` 是 `protected` + 类为 `MinimalAPI` ⇒ 编辑器写入用**反射**（`FindPropertyByName` + 赋值，约 5 行）。


### 5.2 模块 = 多个 fragment 的**闭包**，多个模块按**并集**合成

- 模块不和一个 fragment 一一对应：`Vision` 需要 `FAgentRadiusFragment`/`FAsceHeightFragment`（眼高）+ `FAsceVisionViewFragment` + `FAsceVisionFogStateFragment`；
  `Movement` 也要 Radius/Height ⇒ **两个模块共享同一批 fragment 是合法的**。
- 合成规则：**`FinalFragments = ⋃(每个模块的闭包)`**（集合语义；重复只保留一份）。
- 实现方式：**每次从当前模块列表重算并集**（无状态）。编辑器侧维护"引用计数"也可以，但只用于增量优化；
  "重算"更不容易出 bug（不会漏减、不会残留幽灵 fragment）。
- ⚠️ 若最终产物是**现有 trait + 开关**（方案 A），则不需要算 fragment 并集 —— `UAsceRTSUnitTrait` 内部决定加哪些；
  只有走"显式 fragment 列表 + 通用 trait"（方案 B）时才需要。

### 5.2b 什么时候写回

| 时机 | 做什么 |
|---|---|
| **编辑中**（增删模块 / 改参数） | 只更新**内存草稿 + 预览面板**（几何/动画/fragment 列表/字节数）；不碰 DA、不碰表 |
| **保存** | 重算并集 → 写 trait DA（`Assorted Fragments` 的 fragment + **数值**）→ 写 def 的"非 fragment 字段"→ 写 `Hash` |
| **打开** | 读 `ModuleConfig` 还原模块；对比 `Hash`，检测"DA/表被手改"，提示保留/重置 |

> 并集是内存里的集合运算（微秒级），每帧算也不贵；但**落盘只在保存时**，避免编辑器里到处触发资产重存。

### 5.3 模板落地的两条路
| 路线 | 做法 | 何时用 |
|---|---|---|
| **A. 生成模板资产** | 编辑器按"模块组合"去重，生成/更新 `UMassEntityConfigAsset`，自动填 `Row.EntityTemplate` | 先做，零运行时风险 |
| **B. 运行时组合** | 直接 `GetOrCreateArchetype(Composition, SharedFragmentValues)` 按 def 行缓存 | 后做，可支持热改；需处理 const shared（树/复制参数） |

### 5.4 编辑器预览分级
| 级别 | 内容 | 备注 |
|---|---|---|
| L1 | 占格框 / 视野圈 / 攻击圈 / 数值标注 / **fragment 清单 + 每实体字节 + archetype 组合统计** | 必做，性价比最高 |
| L2 | 直接播动画资产（Idle/Move 变体、Attack 片段），不走 Mass，不需要 PIE | 强烈建议 |
| L3 | 隔离 preview world 里真跑 Mass + StateTree + VAT，输入切状态 | 单独立项 |

### 5.5 动画归属（**cue 驱动**，不要 archetype shared data）

现状（`3c0db39` + `78f9be0` 之后）：
- 单位 `Idle/Move/Attack`：由 `AscePlayIdleAnimTask` / `AscePlayMoveAnimTask` / `AscePlayAttackAnimTask`
  从**单位 def** 的 `IdleAnim / IdleBreakAnims / MoveAnim / RunAnim / InjuredMoveAnim / AttackAnims` 选片段；
  技能链/动作行仍可用 `FAscePlayAnimCueTask` 的节点 `Variants`；
- 这些 task 把"AnimSet 里的烘焙帧号 / 帧率 / 循环 / 播放速率"写进 `FAsceAnimPlaybackFragment::Cue*`；
- 客户端 `UAsceCombatVisualProcessor` **只按 cue 逐帧播**（旧的"按 ActionState/类型解析动画"整段已删除）；
- `FAsceRTSUnitDef` 保留 `AnimSet`（clip 目录：动画资产 → 烘焙帧号）+ 上述状态动画数组；
- `FAsceAnimPlaybackFragment` 只在客户端写（专用服务器早退），**不复制**。

| 层级 | 存什么 | 为什么放这 |
|---|---|---|
| 树节点（cue） | `Variants[]`（该状态可用片段）、`bLoop`、`bHoldState`、`PlayRate` | "状态 → 动画"的直接映射，跟状态机放一起最直观 |
| 单位表 | `AnimSet` | clip 目录属于"这套模型有哪些动画"，与状态无关 |
| 客户端 fragment | `Cue*`（帧号/帧率/循环/速率/计数器） | 纯 POD、per-entity、不复制 |

**要不要用 archetype shared data？不要**：
- 现在每次**进入状态**只做一次 `clip → AnimSet.Clips` 查表（TMap find），之后每帧只推进帧号；
- 放 const shared 会**按动画集分叉 chunk**（archetype 不变，但每种动画集独占一块 chunk），尾块浪费照旧，且每块要多存一份共享值；
- 放 per-entity 更糟（动画引用几百 B × N 实体）。

> ⚠️ **可优化**：`FAscePlayAnimCueTask::EnterState` 每次进入状态都会 `GetEntityDefRow` + `AnimSet.LoadSynchronous()` +
> `Clips.Find()` ⇒ 建议按 `UniqueTypeId` 缓存 `AnimSet` 与 clip 表（现在没有缓存），否则高频切状态时会反复同步加载。

### 5.6 攻击：**动作行的 SkillTree**（`CastConfig` 已退役）

现状：
- **攻击 = 一个动作行**：`FAsceRTSUnitDef::AttackAction` → `FAsceActionDef{ ReleaseMode=Auto, SkillTree }`；
- 单位树的 `Attack` / `Casting` 状态里挂 **`Asce Run Ability Tree`**（`FAsceRunAbilityTreeTask`）：读
  `FAsceActionFragment::ActionDefId` → 动作行 → 跑该行的 **`SkillTree`**（Mass 感知子上下文：复用父 `FMassExecutionContext` + entity，
  外部数据按子树自己的 schema 重新收集）；
- `AsceCombatProcessor` 只剩三件事：Idle/Move 切换、0.3s 目标扫描、**进入 Attack**（写 `ActionState=Attack` /
  `StartServerTime` / `ActionDefId=AttackActionId` / `Counter++`）。施法/攻击的**推进与结算全在树里**，
  `Asce.Combat.TreeDrivesCasting` 开关已删除。
- ⇒ **攻击的时长与动画跟着"动作行"走**：同一行被多个单位引用，它们共享前摇/后摇/动画。

**已经落地的部分 / 仍需注意的两件事**：

| 项 | 现状 | 方案 A（省事，推荐先这样） | 方案 B（灵活） |
|---|---|---|---|
| 前摇/后摇 | 树节点常量 `Asce Wait Timeline.Time`；可用节点上的 `ScaleMode=AttackSpeed/CastSpeed/Constant` 按攻速/施法速度缩放 | **动作行 = 武器类型**，单位只选行，同类武器共用节奏 | 若需要按单位独立的“前摇/后摇基础值”，再加 `FAsceWaitActionPhaseTask{Windup\|Recovery}` 从复制属性读时长 |
| 攻击动画 | 已由 `AscePlayAttackAnimTask` 从单位 def 的 `AttackAnims` 随机选；技能链仍可用 cue 节点 `Variants` | 按单位配 `AttackAnims` | cue 任务 `Source = NodeVariants \| DefVariants` 作为兼容方案（见 §6.6） |

> 判断依据：如果同类武器（比如"步枪兵/狙击手"）本来就要不同节奏和动画，它们**本来就该是两个动作行** ⇒ 方案 A 足够；
> 只有当"同一种攻击、不同单位节奏不同"（比如攻速差异）成为常态时才值得上方案 B。

### 5.7 模块内的 fragment 两分法：**属性（复制）** + **运行态（权威/本地）**

> 原则：一个功能模块 = **属性 fragment**（纯数据，客户端要读的就开复制）+ **运行态 fragment**（服务器专有或本地）。
> 先例：Health/Mana 已经就是这个形态（`FAsceHealthFragment` / `FAsceManaFragment` 走"值通道"复制）。

| 模块 | 属性 fragment（复制条件） | 运行态 fragment（服务器/本地） |
|---|---|---|
| Health | `FAsceHealthFragment`（**已复制**：Max/Current） | — |
| Mana | `FAsceManaFragment`（**已复制**：Max/Current） | — |
| Movement | `FAsceMovementSharedFragment`（BaseMoveSpeed，**const shared 不复制**：trait 从 def 烘焙，两端同值） | Velocity / Force / DesiredMovement / MoveOrder / SimState / PositionCorrection |
| Combat | `FAsceCombatAttributesFragment`（**已复制**：AttackRange / AttackDamage / AttackSpeed / RangeKind / AttackActionId，见 §6.4 的通道） | `FAsceCombatFragment`（瘦身：DesignatedTarget / NextScanTime） |
| Vision | `FAsceVisionViewFragment`（SightRadius/EyeHeight；**不复制**，雾在服务端算） | `FAsceVisionFogStateFragment`（本地） |
| Skills | `FAsceSkillSlotsFragment`（**已复制**：槽位 + CD） | — |
| Interaction | `FAsceInteractableFragment`（Range；**不复制**，判定在服务端） | — |

**只复制"客户端真的会读"的**：Combat 属性必须复制（客户端也要跑攻击子树、要算 PlayRate/动画、要显示攻击范围）；
Movement 的 `BaseMoveSpeed` 是 const shared（两端都从 def 烘焙同一份）⇒ 不需要通道。

**`FAsceCombatAttributesFragment` 字段（24B，**已落地**）**
```cpp
float AttackRange;         // 攻击距离（cm；服务端判定 + 客户端画范围圈）
float AttackDamage;        // 攻击力（动作行 Damage=0 时用它）
float AttackSpeed;         // 180 = 1.0x；决定动画 PlayRate
EAsceRangeKind RangeKind;  // 近战表面 / 远程高地口径
int32 AttackActionId;      // 攻击行 id（0 = 没配攻击行）
// 注：`BaseWindup/BaseRecovery` 没有落地——前摇/后摇写在攻击行的 SkillTree 节点里；
// 注：`bAutoAttack` 已删除（攻击完全由树驱动）。
```

**攻速 → 动画播放速率 / 时间轴速率换算**
```cpp
PlayRate = clamp(AttackSpeed / BaseAttackSpeed, 0.05, 4.0)   // 默认 180/180 = 1.0
```
- `AscePlayAttackAnimTask` 用这个 PlayRate 播攻击动画（再乘节点上的 `PlayRateScale`）；
- 攻击时长用 **`Asce Wait Attack Timeline`**：`Target = 进入节点时刻 + BaseAttackTime × TimeRatio / (AttackSpeed / BaseAttackSpeed)`；
  `TimeRatio` 默认 1（整段），前摇/后摇可拆成两个节点（如 0.7 / 0.3）；
- `AsceWaitTimelineTask` 的 `ScaleMode` 可选：
  - `AttackSpeed`：`Target = Time / (AttackSpeed / BaseAttackSpeed)`；
  - `CastSpeed`：`Target = Time / (1 + CastSpeedPercent / 100)`；
  - `Constant`：`Target = Time`；
- 动作的时长/结算时刻在树里（`AsceWaitTimelineTask` + `AsceSettleSkillTask`）；
- 绝对时刻只在服务器写（`FAsceActionFragment::StartServerTime`），客户端用 `ActionStartTimeQ` 锚定自己的时间轴。

**新增一个复制通道的成本**（照 `AsceReplicationValueHandlers.h` 头注释的 5 步，攻击属性通道已按这套落地）
1. 选/加值容器 USTRUCT（已有 `FReplicatedValueFloat`，直接用）；
2. 写 `FAsceCombatAttributesPolicy`（FragmentType / NumFields / Get(Mutable)Data / ExtractFromFragment / ApplyToFragment / ValuesDiffer）；
3. `using FAsceCombatAttributesClientBubbleHandler = TAsceValueClientBubbleHandler<...>;`
4. `using FAsceCombatAttributesReplicationCapability = TAsceValueReplicationCapability<...>;`
5. `AsceReplicationBootstrapSubsystem.cpp` 里 `RegisterCapability(MakeUnique<...>())` 一行。

> 实测：`FAsceCombatAttributesFragment` 24B、`FAsceCombatFragment` 16B（原来合在一起 40B）。
> 拆开的理由不是省字节，而是"属性要复制、运行态不能复制"，一个 fragment 只能选一边。


### 5.8 数值烘进 DA；def 表只留"引用 + 非 fragment 数据"

**为什么可以烘**：每类型一个 DA ⇒ 不存在"共享 DA 时数值被共享"；
模板里的 fragment 初值会在 `SpawnEntities` 时**逐实体拷贝**（=`该类型的默认值`）；
两个类型 fragment 集合相同时仍是**同一 archetype**（值不影响 archetype），各用各的初值。

**能搬进 DA 的（都是 fragment 的值）**

| 原 def 字段 | 目标 fragment |
|---|---|
| `BaseMoveSpeed` | `FAsceMovementSharedFragment`（const shared，trait 从 def 烘焙） |
| `Radius` / `Height` | `FAgentRadiusFragment` / `FAsceHeightFragment` |
| `MaxHealth` | `FAsceHealthFragment`（Max = Current = 值） |
| `MaxMana` | `FAsceManaFragment`（Max = Current = 值） |
| `SightRadius`（EyeHeight 取 Height） | `FAsceVisionViewFragment` |
| `AttackRange / AttackDamage / AttackSpeed` | `FAsceCombatAttributesFragment` |
| `InteractionRange / bPlayerOnlyInteraction` | `FAsceInteractableFragment` + tag |
| （动画播放初值） | `FAsceAnimPlaybackFragment` |

**必须留在 def 表的**

| 字段 | 为什么 |
|---|---|
| `EntityTemplate` | 就是 DA 引用本身 |
| `AnimSet` | **不是 fragment**（Mass fragment 必须 POD，不能放 UObject/软引用）；`AscePlayAnimCueTask` 经 `UniqueTypeId → def 行 → AnimSet` 取 clip 表 |
| `AttackAction` / `SkillSlots[3]` | 是**行名引用**（经 `FAsceActionDefLibrary` 解析 + 校验 ReleaseMode）；动作行跨单位共享，烘成 int 会丢改名自动更新 |
| UI（DisplayName / Description / HeadIcon） | 与实体无关 |
| 建筑：`SizeX/SizeY/OcclusionHeightCm/BuildTimeSeconds/CoreClass` | 不是 fragment；建筑子系统运行时按 def 行构造/校验，Ether 也按行拷贝 |
| Ether：`DeviceType/ProcessCore/PortSlots/DefaultInternalLinks/...` | 同上 |

**三个要跟着改的地方**

1. **`ApplyUnitDef` 瘦身**：不再从 def 写那些数值（否则覆盖回旧值）。只保留 spawn 时写的：
   - `FAsceTeamFragment::TeamKey`（每队不同）
   - `FAsceUnitDefFragment::UniqueTypeId`（每类型一个 DA ⇒ 可以继续烘；想共享 DA 才挪到 spawn）
   - 若 DA 里烘的是"满血满蓝"，`CurrentHealth/CurrentMana` 不需要额外写；
2. **攻击/技能的"数值 → 动作行"解析挪到烘焙期**：现在工厂里的"`Range/Damage` 为 0 跟随属性、`ReleaseMode` 要 Auto/Manual、槽位查不到告警"，
   全部改成**编辑期解析 + 校验**（面板直接报错，比运行时日志好）；
3. **`FAsceCombatFragment` 的运行时字段**（`DesignatedTarget`、`NextScanTime`）保持默认值，不烘任何东西。

**结论**：DA = 结构 + 数值（每类型一份，可读可 diff）；def = 引用 + 非 fragment 数据；spawn 时只写"每实例/每局变化"的东西。

## 6. 风险 / 未决

### 6.1 archetype 数 / chunk 数（**两个不同的东西**）

> **Archetype 身份 = composition 的"类型"集合**：fragment 类型 + tag 类型 + shared/const-shared fragment **类型** + groups。
> `FMassEntityManager::CreateArchetype` 的判定是 `IsEquivalent(Composition)`（`MassEntityManager.cpp:378-401`）。
> **shared / const-shared 的"值"不在 archetype 身份里**，它们存在 **chunk** 上（`FMassArchetypeChunk::SharedFragmentValues`），
> 实体按自己的值匹配到对应 chunk（`MassArchetypeData.cpp:238` 的 `Chunk.GetSharedFragmentValues().IsEquivalent(...)`）。

| 变化 | 影响 |
|---|---|
| 模块组合变了（fragment/tag 集合变） | **新 archetype** |
| StateTree 换了（const shared 值变） | **archetype 不变**，但**新 chunk**（同 archetype 下按值分块） |
| `ReplicationTuning` 改值 | 同上：**chunk** 级，不是 archetype |
| 同一份模块组合 + 同一套 shared 值 | **同一个 archetype、同一个 chunk 池** |

结论：
- **archetype 数 = 模块组合数**（不是单位类型数）⇒ 编辑器显示"全项目 N 种组合"就是在算 archetype 数；
- **chunk 数/浪费 = 每个 (archetype × 每套 shared 值) 至少 1 个 chunk** ⇒ 每类型一棵树仍然各自占 chunk，128KB 尾块浪费照旧；
- 合并策略仍值得：能共用组合就共用（例如所有地面战斗单位统一勾 Health+Volume+Movement+Vision+ActionState+Animation+Combat）；
- 顺带：`ChunkMemorySize` 是全局的；同一 archetype 用不同 chunk 大小会被忽略并告警（`CreateArchetype` 复用已有 archetype 的块大小）。


### 6.2 `bCanAttack=false` 目前会连技能一起废掉（**必须先修**）
`UAsceCombatProcessor` 的 query 把 `FAsceCombatFragment` 设为**必需**，而它是动作状态机（Move/Casting/Channel 推进）的唯一驱动者 ⇒ 没有战斗模块的单位：
- 技能 `Casting` 卡死、`ActionState=Move` 永远不写（走路不播动画）。
- 修法：把该 fragment 改成 `Optional`，攻击相关代码进 `if (bHasCombat)`；状态机无条件跑。或更彻底：拆出 `UAsceActionProcessor`（只要 `FAsceActionFragment`）。

### 6.3 通用树前提（否则"一棵树"不成立）

- ~~`AsceSelectAnimVariantTask` 挪进 notify processor~~ —— **已完成**（`3c0db39` 删掉了该 task；变体现在在 `Asce Play Anim Cue` 节点里随机选）
- 能力 tag（`Asce.Capability.Move/Attack/Cast`）+ `FAsceStateTreeTagCondition`（约 40 行）⇒ 状态按能力裁剪
- **新前提**：动画/时长现在挂在**树节点**（cue 的 `Variants`、`Asce Wait Timeline.Time`）⇒ 一棵通用树会丢掉"每单位不同动画/节奏"。
  要么接受"同类武器共用一套"（用动作行区分），要么给 cue / wait 加"从数据读"的模式（见 §6.6）
- 之后 `FAsceEntityDefBase::StateTree` 留空 = 用通用树

### 6.4 编辑器成本主要在预览
L1 便宜；L2 要处理"编辑器里没有 Mass 世界"的资产加载；L3 是独立小项目（preview world 隔离、输入、状态驱动）。

### 6.5 迁移

**不做迁移工具**：目前只有两个配置，改成"新配"即可（用新编辑器重新勾模块 → 生成 DA/表）。
以后单位配置多了，再考虑写一次性推导工具（见 §5.1 附近的推导规则）。

### 6.6 待决策：动画/时长留在树里，还是挪到数据

现状（`3c0db39`）把**动画变体和时间轴门槛都放进了树节点**，这带来一个直接冲突：

| 目标 | 树节点配置（现状） | 数据配置 |
|---|---|---|
| 改一个单位的动画 | 改它的树（或换动作行） | 改表一行 |
| 多单位共用同一套树 | ❌ 做不到（动画在树里） | ✅ 天然可以 |
| 在单位可视化面板统一配动画 | 要去树编辑器里配 | 在单位编辑器里配 |
| 修改成本 | 每种树各改一遍 | 一处 |

**已落地且问题不大**：攻击/技能 = 动作行 + `SkillTree`（同类武器共用）。
**真正的冲突**：`Idle/Move/Dying` 这类"每单位都不同"的动画现在也在树节点里（每个单位的树各配一套 cue）。

**建议（等模块化时一起做）**：
1. `FAscePlayAnimCueTask` 加 `Source`：`NodeVariants`（现状）/ `DefVariants`（从单位表动画模块读数组）。
   `Idle/Move/Dying` 用 `DefVariants`，攻击/技能用 `NodeVariants`（跟动作行走）；
2. `Asce Wait Timeline` 同理加 `Source`：`Fixed`（现状）/ `FromCombatAttributes`（前摇/后摇），
   只有"同一动作、不同节奏"时才需要；
3. 这样通用树才真正成立：**树只表达状态与流程，动画/时长走数据**，可视化面板改数据即可。
