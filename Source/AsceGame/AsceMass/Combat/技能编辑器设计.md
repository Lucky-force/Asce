# 技能运行时与编辑器（Mass × StateTree，运行时已落地、待配资产验收）

> 状态：**§1–§10 运行时代码已落地（待配资产 + 验收）**；§11 作弊系统**第一批已落地**（注册表/门控/权限开关）。
> 相关：`Combat/技能系统设计.md` §10（编排模型/时间轴/两端同步）、`Networking/Mass复制设计.md`、`UI/UI.md`。
> **结论**：运行时用引擎自带的 **Mass × StateTree**（不自己写调度器）；技能是**独立的 StateTree 资产**；
> 单位是**每类型一棵小树**（只 4 个外层状态 + 一个通用"跑技能子树"任务）；时间轴只在 **Attack / Casting** 的子树里。

## 1. 选型与理由

| 方案 | 结论 |
|---|---|
| **Mass × StateTree** | ✅ **采用**（见 §2 引擎事实） |
| 自研时间轴运行时（`UAsceTimelineRunner` + 两个 processor） | ❌ 否决：实例数据池化、生命周期、并行、编译期优化、调试器都要自己写/自己调 |
| 每次施法生成"动作实例实体"（每技能一棵树的 archetype） | ❌ 否决：每次施法都要结构变更 + 池槽获取/释放（串行），替换/打断还要销毁重建 |
| Sequencer（MovieScene） | ❌ 不进运行时：world/actor 级、无多人复制、不适合逐实体 |
| 纯 StateTree 状态链 + unroll 重复 | ❌ 否决：持续施法用一个会 tick 的 task 即可，不需要展开 |

## 2. 引擎事实（依据，`Plugins/AI/MassAI/Source/MassAIBehavior/*`）

- **树只有一份**：`FMassStateTreeSharedFragment` 只存 `TObjectPtr<UStateTree>`，是 **shared fragment（按 archetype 一份）**，不是 per-chunk/ per-entity。
- **每实体只有 16B + 一个池槽**：`FMassStateTreeInstanceFragment{ FMassStateTreeInstanceHandle InstanceHandle; double LastUpdateTimeInSeconds; }`；
  实例数据在 `UMassStateTreeSubsystem` 的**扁平 `TArray` + freelist + Generation**（`MassStateTreeSubsystem.h:88-91`）。
- **processor 按 requirements hash 复用**（`MassStateTreeSubsystem.h:114` 注释：多棵树 requirements 相同则**共用一个 processor**，一个 processor 里存 `HandledStateTrees` 数组）。
- **任务能直接摸实体**：`FMassStateTreeExecutionContext` 继承 `FStateTreeExecutionContext` 并复用 `FMassExecutionContext`（`GetEntity()/GetEntityManager()`），`SetEntity`。
- **实例数据的分配是串行的**（`MassStateTreeSubsystem.h:93-99` 的 MT 检测 + 引擎 TODO 写明"activation 不能并行"）⇒ **挂树放在生成阶段做一次**。
- **状态选择是"按优先级遍历转移"**（`StateTreeState.h:80-126`）：每个 tick/事件，对当前状态的转移**逐条**看 trigger → 条件 → **第一个命中即停**；
  转移可带 **`RequiredEvent`（`FGameplayTag`）** ⇒ 事件派发只比较 tag，**不要用 `OnTick` + 条件链轮询**。
- **linked tree 支持运行时按 tag 选**：`FStateTreeReferenceOverrides`（`tag → FStateTreeReference`）+ `SetLinkedStateTreeOverrides` / **`GetLinkedStateTreeOverrideForTag`**（`StateTreeExecutionContext.h:344-358`；内部 `FindByPredicate`，**O(N)**）。
- **可在任务里跑另一棵树**：`FStateTreeRunParallelStateTreeTask`（`StateTreeRunParallelStateTreeTask.h`；⚠️ **本机 5.7 里 `GetStateTreeToRun()` 不是 virtual**，选树方式见 §3.1）；
  `FStateTreeReference` 支持**参数覆盖**（`SyncParameters` / `K2_SetParametersProperty`）⇒ 子树能接收 caster/target 等参数。
- ⚠️ **MassAI 默认只跑服务端**：`UE::MassStateTree::ExecutionFlags = Standalone | Server`（`MassStateTreeTypes.h`），
  用在 `UMassStateTreeActivationProcessor`（分配实例数据 + 发激活信号）/ `UMassStateTreeFragmentDestructor` / `UMassStateTreeProcessor`（tick）三处
  —— 因为 MassAI 是 **AI** 模块，默认假设"每实体状态树 = AI 行为"。
- ★ **但可扩展（官方扩展点，不是 hack）**：
  - `UMassBehaviorSettings::DynamicStateTreeProcessorClass`（`TSoftClassPtr<UMassStateTreeProcessor>`）是**官方扩展点**
    （`MassStateTreeProcessors.h:69` 注释："a project-specific extension can be implemented…"）；
  - `ExecutionFlags` / `bRequiresGameThreadExecution` 在 `UMassProcessor` 里是 **protected**（`MassProcessor.h:224/235`）⇒ 子类构造可改；
  - 三个 processor 的 ctor 都是导出（`MASSAIBEHAVIOR_API`）⇒ 可子类化。
- ⚠️ **MassAI 是实验性插件**（`IsExperimentalVersion=true`、`EnabledByDefault=false`）；`MassAIBehavior` 依赖
  MassNavigation / MassNavMeshNavigation / MassZoneGraphNavigation / MassSmartObjects / ZoneGraph / ZoneGraphAnnotations /
  NavCorridor / NavigationSystem（`MassAIBehavior.Build.cs`）⇒ 代价是**编译面/磁盘**（没实体用就不会跑）。

## 3. 组织结构（定稿）

```
每个"单位类型"一棵树（构建期决定：def 行 → EntityTemplate → 树资产）
  Idle     —— 纯表现（随机待机）
  Move     —— 纯表现（按当前速度选移动动画）
  Attack   —— 攻击子树（**有时间轴**）；可多个变体（随机，两端不一致可接受）
  Casting  —— 通用任务 RunAbilityTree：按 [当前槽位的技能 id] 从 TMap → UStateTree **O(1) 查表**，
              跑该技能的独立子树（**时间轴节点在技能子树里**）
  （Dying：**不进树** —— 沿用现有死亡设计：置 Dying ⇒ 隐藏 ⇒ 复制移除 ⇒ 销毁）
```

- ★ **技能不进单位树**：每个技能 = 一个**独立 StateTree 资产**；新增技能**不需要改任何单位树**，也不会出现"link 全部技能"。
- ★ **类型维度在构建期**：单位树按类型分离（每类型一棵），所以 `idle/move/attack` 的资产直接挂在自己树里，**树内不需要 rowid/tag 判断**。
- **外层状态与 `FAsceActionFragment` 单向同步**：
  - 系统（指令 / 战斗扫描）写 fragment + **发事件** → 树进入对应状态；
  - 树完成/被打断 → **回调系统**，由系统写 fragment（回 `Idle` 等）。
  - 树**不反向写** fragment（复制仍以 fragment 为唯一真相，动作态通道不变）。
- **时间轴只在 Attack / Casting**；Idle/Move 是"持续播放 + 状态硬切"，没有逻辑节点。

### 3.1 子树任务：**直接用**引擎的 `FStateTreeRunParallelStateTreeTask`

- 引擎自带、**公开导出**（`STATETREEMODULE_API` 的 `USTRUCT`，编辑器里显示为 "Run Parallel Tree"）。
- 它已经提供了我们要的东西：
  - **完成信号**：子树的 **成功 / 失败 / 进行中自动反映成这个任务的状态** ⇒ 父状态自然结束，**不用自己写回调**；
  - **每实体按需选树**：任务实例数据里的 `FStateTreeReference StateTree`（+ 子树的 `FStateTreeInstanceData`）是**按实例（= 按实体）**的
    ⇒ 想在哪个实体上跑哪棵技能树就改这里。★ **这就是"每实体按需选树"的唯一槽位**（树结构本身是编译期共享的，实例数据里不存"选了哪棵树"，除非是这种持有 `FStateTreeReference` 的任务）；
  - `StateTreeOverrideTag`：配 `SetLinkedStateTreeOverrides` 可按 tag 替换要跑的树（引擎自带）；
  - ⚠️ **`GetStateTreeToRun(Context, InstanceData)` 在本机 5.7 里不是 virtual**（`StateTreeRunParallelStateTreeTask.h:88`）⇒ **不能**用"覆写它"做 O(1) 选树。两种可行路子：
    ① **覆写 `EnterState`**（是 virtual）：先用 `TMap<int32 /*技能 id*/, FStateTreeReference>` 填好
       `InstanceData.StateTree`，再调 `Super::EnterState`（`GetStateTreeToRun` 会在没有 override tag 命中时用 `InstanceData.StateTree`）；
    ② **`StateTreeOverrideTag`** + 每次施法调 `SetLinkedStateTreeOverrides`（内部 `FindByPredicate`，但列表长度通常 = 1 ⇒ 实际 O(1)）。
    5.8 机器上要复核 `GetStateTreeToRun` 是否改成 virtual；以引擎头文件为准。
- ⚠️ 它自己的注释写明 **"less efficient than Linked Asset"**（独立子树实例数据 + 并行事件处理），但换来**运行时任意选树**——
  **没有更省的同功能方案**（见下）。
- ⚠️ **不要自己重写**：那等于重做"子上下文创建 + 实例数据生命周期 + **按拍调度 `ScheduleNextTick`** + 状态回传 + 事件优先级 + 编辑器集成"。
- ⚠️ 三条替代路都更差：
  1. **每个技能一个状态分支 + 静态 linked asset** ⇒ 单位树要 link 全部技能（正是要避免的），且选择要么 OnTick 轮询、要么 N 条带 `RequiredEvent` 的转移；
  2. **换实体树**（改 `FMassStateTreeSharedFragment`）⇒ 每次施法 **archetype 变更** + 树实例重建；
  3. **自己写跑子树任务** ⇒ 重写上面那堆。
- ⚠️ `FStateTreeReferenceOverrides` 是"按 **state tag** 替换某状态的 linked tree"，**不能**当技能选择器（一个 `Casting` 状态只有一个 tag，选不了 N 个技能）。
- ⚠️ 注意：子树**并行**跑（父树继续 tick/处理子状态）⇒ `EventHandlingPriority` 建议设 **Low**（父树先处理打断/停止）；
  子树 schema 必须与父树兼容（Mass schema）。

### 3.2 两笔账：**资产大小** ≠ **每实例内存**

- ★ **实例数据只装"全局 + 当前激活路径"**（`StateTreeInstanceData.h:327-339` 的布局注释）：
  `Global 参数 / Global 节点实例(evaluator, global task) / 激活状态参数 / 激活的 task 实例`。
  ⇒ **没激活的分支不进实例数据**——技能树资产可以有很多状态/分支，**不会**把每个实例撑大。
- ★ **资产（`UStateTree` 编译数据）是"整棵树、一棵一份、所有实体共享"**：规模取决于**整棵树的结构**
  （状态/任务/条件/转移表数量）⇒ 影响的是**资产内存/加载/编译时间**、以及"每 tick 遍历转移"的成本，**不是每实体内存**。
- ★ **容量会保留**：`ExitState` 只 `Stop()`、不释放实例数据 ⇒ 每个单位保留**它跑过的最大那条激活路径**的容量。
- 结论：**"让每实例小" = 控制激活路径上 task 的 `instance data`（大小/数量）**，而不是砍状态总数；
  一个线性的技能链（根→当前节点）本身很小。`RunParallel` 的子实例数据同理（只装子树的激活路径）。

### 3.3 两端都跑（方案 A）：3 个薄子类

MassAI 默认只服务端，但用官方扩展点可以**让客户端也跑**（这样"逻辑/表现同一条树、按端早退"才成立）：

| 子类 | 基类 | ctor 改动 | 注册方式 |
|---|---|---|---|
| `UAsceStateTreeProcessor` | `UMassStateTreeProcessor` | `ExecutionFlags = AllNetModes` | 配到 `UMassBehaviorSettings::DynamicStateTreeProcessorClass`（**官方扩展点**） |
| `UAsceStateTreeActivationProcessor` | `UMassStateTreeActivationProcessor` | `ExecutionFlags = AllNetModes` | 自动注册；**ini 关掉引擎默认那个** |
| `UAsceStateTreeFragmentDestructor` | `UMassStateTreeFragmentDestructor` | `ExecutionFlags = AllNetModes` | 自动注册；**ini 关掉引擎默认那个** |

- ⚠️ **为什么必须"关掉引擎默认 + 我们三端都跑"**：听服世界的 exec flags = **`Client | Server`**（见项目 `DefaultMass.ini` 的注释），
  所以"引擎版(`Standalone|Server`) + 我们的 `Client` 子类"会在听服上**同时命中** ⇒ 实例数据重复分配/重复激活。
  正确做法 = `DefaultMass.ini` 里把 `MassStateTreeActivationProcessor` / `MassStateTreeFragmentDestructor` 的
  `bAutoRegisterWithProcessingPhases=False`，由我们的子类用 `AllNetModes` 统一接管。

- ★ **我们自己的 trait 必须两端都挂**：`FMassStateTreeSharedFragment{树}`（const shared）+ `FMassStateTreeInstanceFragment`
  —— **不能**照抄引擎 trait 的 `Standalone|Server` early-return；这样两端 **archetype 也一致** ✓。
- ⚠️ 客户端实例数据分配是**串行 + 必须 GameThread**（引擎为此设 `bRequiresGameThreadExecution=true`）⇒ 一批单位进视野会集中分配，需实测。
- ⚠️ 客户端跑树**只能做表现**（不得产生权威副作用）⇒ 靠 task 按端早退：**逻辑 task 在客户端早退、表现 task 在服务端早退**。

## 4. 调度与开销

- **外层状态的转移用 `OnEvent`（+`RequiredEvent`）**：单位事件只来自系统（`CastSkill` / `Attack` / `Stop` / `Move`…），
  ⇒ **idle 单位每帧不评估任何条件链**。
- **技能选择 O(1)**：`RunAbilityTree`（= §3.1 的 `FStateTreeRunParallelStateTreeTask` 或其 20 行子类）用
  `TMap<int32 /*技能 id*/, FStateTreeReference>` 查表（**不要**用 `FStateTreeReferenceOverrides` 当技能选择器——
  它是按 state tag 替换；也不要把技能做成 N 条 OnTick 转移）。
- **嵌套子树**：子实例数据**随任务实例数据常驻**（只装子树的激活路径，见 §3.2）；每次施法只是 `Start()`/`Stop()`
  （**容量复用**，不是每次重新分配）——真正要避免的是"在战斗中途反复加/减带树的 fragment"（实例数据分配是串行的，放生成阶段）。
- **单位树在生成阶段挂一次**（`InstanceHandle` 分配一次），战斗中**零结构变更**。
- **可开 `bProcessEntitiesInParallel`**（`UMassStateTreeProcessor` 的配置）；task 写 fragment 要守 Mass 线程规则。

### 4.1 事件路径（系统 → 树）

`AsceStateTree::SendEventToEntity(World, EntityManager, Entity, Tag, Payload, Origin)`（`Behavior/AsceStateTreeEvents.h`）：

1. `FMassStateTreeInstanceFragment.InstanceHandle` → `UMassStateTreeSubsystem::GetInstanceData(...)`；
2. `FStateTreeInstanceData::GetMutableEventQueue().SendEvent(Owner, Tag, Payload, Origin)` **入队**（队列上限 64）；
3. `UMassSignalSubsystem::SignalEntity(UE::Mass::Signals::NewStateTreeTaskRequired, Entity)` **唤醒**。

- ★ 树是**信号驱动**的（`UMassStateTreeProcessor : UMassSignalProcessorBase`）：**不发信号，事件会一直躺在队列里**
  等下一个外部信号才被处理（会"延迟生效"甚至不生效）。
- ★ 每次信号 tick 的 delta 由 `FMassStateTreeInstanceFragment::LastUpdateTimeInSeconds` 算（**墙钟差**）⇒ 卡顿会被吸收（不是逐帧累加）。
- 转移条件写 `RequiredEvent = <Tag>`；事件派发只比较 tag，不会把 OnTick 条件链扫一遍。
- ★ **谁发（B1 的实现）**：不在各状态变化点散插，而是**一个统一 processor**
  `UAsceStateTreeNotifyProcessor`（`Behavior/`，`ExecuteBefore(Behavior)`、`AllNetModes`）：
  两端各自读自己的源（服务器 `FAsceActionFragment` / 客户端 `FAsceCombatVisualFragment`），
  用 `FAsceBehaviorFragment` 里的 `LastNotified*`（**归一状态 + `Counter`**）做**边沿检测**，变了才发
  `Asce.Action.Idle / Move / Attack / Cast`（`Casting/Channel` 归一成同一个、`Dying` 不发）。

### 4.2 时间轴标量 + 逐帧唤醒 + 节点时间门槛（**已落地**）

| 件 | 文件 | 作用 |
|---|---|---|
| 标量 | `Behavior/AsceBehaviorFragment.h` 的 `TimelineStartWorldTime / bTimelineActive` | **绝对时间**，不逐帧累加 |
| 写标量 | `AsceStateTreeNotifyProcessor` | 检测到进入 `Casting/Channel` ⇒ 起轴（`StartWorldTime = 服务器现在`）；回其它状态 ⇒ 清 `bActive`（`Channel` 延续同一条轴） |
| 每帧唤醒 | `Behavior/AsceStateTreeTickDriver` | 给 `bActive` 的实体每帧发 `NewStateTreeTaskRequired`（树是信号驱动，否则时间轴节点不会到点） |
| 节点门槛 | `Behavior/AsceWaitTimelineTask`（"Asce Wait Timeline"） | 进入时比较 `时间轴时间 >= TargetTime`（Target = Time / Rate）：没到 ⇒ `Running`，到点 ⇒ `Succeeded`；转移用 **`On State Completed`**。`ScaleMode`：`Constant` / `AttackSpeed`（`AttackSpeed / BaseAttackSpeed`）/ `CastSpeed`（`1 + CastSpeedPercent/100`） |
| 时钟 | `Behavior/AsceTimelineLibrary` | 一律用 `GetServerWorldTimeSeconds()`（客户端也拿得到，是同步时钟） |

- 用法示例：`Casting` 状态挂 `Asce Wait Timeline (0.8, ScaleMode=CastSpeed)` → 转移 `On State Completed` → 下一段状态；攻击子树可挂 `ScaleMode=AttackSpeed`。
- ✅ **施法结算已抽成共享 API**：`Combat/AsceSkillCastLibrary.h` 的 `AsceSkillCast::{ApplyDamage, PayCostAndCooldown, ApplyEffect, SettleFromAction}`；
  树里的**结算节点** = `Behavior/AsceSettleSkillTask.h`（"Asce Settle Skill"，`bPayCost` 区分 Trigger / 周期节点；客户端自动早退）
  （`AsceCombatProcessor` 已改用它，行为不变；**树的 task 下一步直接调这三个**，不用再写一遍结算）。
- ✅ **锚点已接**：`FAsceActionFragment::StartServerTime`（动作开始时写）→ 动作态通道以**回绕百分秒**下发
  （payload +2B，`QuantizeActionStartTime`）→ 客户端 `FAsceCombatVisualFragment::ActionStartTimeQ` →
  `UAsceStateTreeNotifyProcessor` 用**服务器的起点**起轴（而不是"收到边沿的时刻"）。
  - ★ 因为时间轴是**绝对时间**（`服务器现在 − 起点`），锚点一到位两端的**时间轴位置就自动一致**（差一个 RTT/2 的"起播后退"），
    所以**不需要再做速率收敛**；偏差只在"起轴那一刻"一次性完成（≈ 硬切掉前 RTT/2 的动画）。

### 4.3 fragment 粒度（重要）

**按"archetype 成员是否不同"来分 fragment，不要一个字段一个 fragment。**

- Mass 里每个 fragment 都是 chunk 的一列：1 字节的 fragment 也要占一整列 + padding + 遍历开销；
  新增 fragment 还会让**所有单位**的 archetype 变一次。
- 所以"每个实体都有、生命周期相同、都很小"的本端运行态 → **合并成一个**：
  `FAsceBehaviorFragment`（**8B**：`TimelineStartWorldTime(float) + LastNotifiedCounter(uint16) + PackedStateAndFlags(uint8：3bit 状态 + 1bit 时间轴在跑)`）
  —— 时间轴标量 + 动作态通知边沿共用它（**替代**原先分开的 `FAsceTimelineFragment` / `FAsceActionNotifyFragment`）。
  - ★ **`float` 不损失精度**：`AGameStateBase::GetServerWorldTimeSeconds()` 本身就返回 float ⇒ 存 double 只是把结构撑到 8 字节对齐（16B）。
    换成 float 才真的落到 8B；`uint16` 的 `Counter` 只做"变了没有"的比较，回绕无影响。
- 跟"当前播什么"强相关的（变体种子、走/跑档位）→ 放进**已有的** `FAsceAnimPlaybackFragment`，不新开。
- 只有当 **fragment 成员集合本身不同**（例如"只有施法者才有"）或数据较大/需要独立复制时，才值得单开新 fragment。

## 5. 表现细节

- `idle`：✅ **已接**——`AscePlayIdleAnimTask` 循环 `IdleAnim`，并按 4~8s 随机插播 `IdleBreakAnims`（插播期间不累计）。
- `move`：✅ **已接（走/跑/受伤分档）**——`AscePlayMoveAnimTask` 按优先级选桶：受伤（HP < 15%）→ `InjuredMoveAnim`；
  速度 ≥ `1.7 × BaseMoveSpeed` → `RunAnim`；否则 `MoveAnim`。速度读 `FMassVelocityFragment`（复制下来的），
  桶变化才换动画（= 一次边沿）。
- `attack`：✅ **已接**——`AscePlayAttackAnimTask` 从 `AttackAnims` 随机挑一条，`PlayRate = AttackSpeed / BaseAttackSpeed`（× 节点 `PlayRateScale`）；
  攻击行不再有 `AttackCastConfig.CastAnim`。
- **攻击专用等待**：`Asce Wait Attack Timeline`（`AsceWaitAttackTimelineTask`）——基础时长取单位 def 的
  `BaseAttackTime`，节点上的 `TimeRatio` 是**本段**占基础时长的比例（默认 1；前摇/后摇可拆成 0.7/0.3 两个节点），
  目标 = `进入节点时刻 + BaseAttackTime × TimeRatio / (AttackSpeed / BaseAttackSpeed)`；拿不到 def 时用 `FallbackTime`。
  攻击子树优先用它，替代写死 `Time` 的普通 `Asce Wait Timeline`。
- `dying`：不在树里（现有死亡流程/将来的客户端本地死亡特效负责）。
- **树两端都跑**（§3.3）：**表现 task 在服务端早退**（不渲染）、**逻辑 task 在客户端早退**（不产生副作用）；
  变体选择用本地随机即可（**两端不一致已确认为可接受**；想一致就用确定性种子，如 `hash(NetID, Counter)`）。

## 6. 编辑器与预览

- **编辑**：直接用 **StateTree 编辑器**（层级、条件、事件、调试器全部免费）。
- **时间轴视图**：可选、**只读**——由 Attack/Casting 子树里的时间节点（时间门槛/节点时间）推导成一条时间轴，便于看"几秒做什么"。
  （技能子树里的节点 = §10 的"节点模型"；如果最终用"task 内自己 tick + 时间门槛"，视图就按门槛时间画。）
- **预览**：
  - `GEditor->RequestPlaySession(...)` 起**独立 PIE**，加载配置的预览关卡（像普通关卡一样摆好施法者/靶子）；
  - 面板通过 PIE 世界里的运行器驱动"play/pause/scrub"；
  - ★ **StateTree 没有 seek**：scrub = **重置基线（重启 PIE / 重载关卡）+ 推进到目标时间**；
    - **A（跳过）**：编辑器里"强制选中目标状态"（不执行副作用）；
    - **B（快进）**：按时间轴标量往前跑（执行副作用），有界（一帧最多推进 N 个状态或设上限）。
- **自研插件的范围缩到**：可选的"只读时间轴视图" + "预览 harness"。**运行时/调度器不写了**。

## 7. 与 `技能系统设计.md` §10 的关系

- §10.3 的**锚点 + 同步时钟 + 速率收敛**不变：
  - 时间轴标量（`StartServerTime` / `TimelineTime`）存 **fragment**（不复制或只随动作边沿发一次锚点）；
  - 树的条件/节点计时都读这个标量（经 Evaluator/task），**不用 tick 的 raw delta**；
  - 客户端把标量的速率调快/调慢 ⇒ 门槛转移自然跟着变；
  - 硬切三情形（换轴 `Counter` 变化 / 偏差超阈值 / 中断或超时）不变。
- §10.4（攻击 = `ReleaseMode=Auto` 的动作、基础属性、槽位固定 3 + 行名）不变。
- §10.5 的"行为标志"（`bInterruptibleByMove` / `bCancelOnlyByStop` / `bLockFacing`）**体现为树的结构**：
  - 攻击有"移动指令 → 打断"的转移；施法**没有**移动打断的转移，只有 `S`/死亡；
  - 移动层仍要"`Casting` 速度清零但保留订单"（修现有"边施法边滑"）。

### 10.4 已知风险 / 坑

1. **技能必须有 `SkillTree`、单位必须挂单位树**：否则施法订单会被拒绝（`SkillCasterInvalid`，不会卡在 Casting）。

4. **动作态只在服务器写**（`Asce Set Action State` / 结算 task 都在客户端早退）；客户端表现完全靠复制。
5. **`SkillSlots`/`AttackAction` 都是行名**：行名写错时工厂会告警并按空槽/旧路径处理。
6. **`FAsceActionDefLibrary` 索引不热更**：改了动作表要重进 PIE（或调 `InvalidateCache()`）。
7. **实例数据分配是 GT 串行**：树在**生成阶段**挂（trait），不要在战斗中途加/减带树的 fragment。
8. **客户端时间轴是"服务器起点"**：起轴那一刻会跳掉前 ~RTT/2 的动画（已确认为可接受；不需要速率收敛）。

### 10.6 实现备忘（下次改代码前必读）

- **`FAsceBehaviorFragment`（8B）**：`float TimelineStartWorldTime` + `uint16 LastNotifiedCounter` + `uint8 PackedStateAndFlags`
  （bit0..2 上次通知状态、bit3 时间轴在跑）。**只挂在有树的实体上**（`UAsceRTSEntityTrait` 里跟树 fragments 一起加）。

- **execute 顺序**：`UAsceStateTreeNotifyProcessor` / `UAsceStateTreeTickDriver` 都在 `UE::Mass::ProcessorGroupNames::Behavior` **之前**
   （否则本帧的事件/唤醒赶不上树的 tick）。⚠️ `ProcessorGroupNames` 在 **`MassCommonTypes.h`**（不是 DependencySolver）。
- **task 的依赖**：`GetDependencies` 里用 **handle 重载**（`AddReadWrite(Handle)`）可保留 Optional 语义；
  用 `AddReadWrite<T>()` 是**必需**（缺了会让模板校验失败）。
- **计时**：一律 `AsceTimeline::GetServerNow()`（= `GetServerWorldTimeSeconds`，float）；**不要**逐帧累加 delta。
